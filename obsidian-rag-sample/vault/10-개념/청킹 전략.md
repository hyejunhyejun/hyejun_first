# 청킹 전략

청킹은 문서를 **검색 단위**로 자르는 작업입니다. RAG 품질의 절반은 여기서 결정됩니다.

## 원칙

- **한 청크 = 한 가지 이야기.** 검색 결과로 사람이 읽었을 때 그것만으로 말이 되어야 합니다.
- **제목 경로를 함께 저장한다.** `RAG란 무엇인가 > 파이프라인 5단계` 처럼 상위 헤딩을 붙여두면 문맥이 살고, 출처 표시도 정확해집니다.
- **너무 잘게 자르지 않는다.** 200자 청크는 검색은 잘 되지만 답을 쓰기엔 근거가 모자랍니다. 400~1200자가 실무적으로 무난합니다.
- **표와 코드 블록은 쪼개지 않는다.** 반쪽 난 표는 근거로 못 씁니다.

## 마크다운 위키에 맞는 방식

옵시디언 노트는 이미 사람이 헤딩으로 구조를 잡아둔 문서이므로 **헤딩 기준 분할**이 가장 잘 맞습니다.

1. `#`, `##`, `###` 를 기준으로 섹션을 나눈다.
2. 각 섹션에 헤딩 경로와 프론트매터(태그, 제목)를 메타데이터로 붙인다.
3. 너무 짧은 섹션(예: 100자 미만)은 다음 섹션과 합친다.
4. 너무 긴 섹션은 문단 경계에서 자르되 **1~2문단 겹치기(overlap)** 를 준다.

겹치기를 주는 이유는 경계에 걸친 문장이 어느 쪽에서도 검색되지 않는 사고를 막기 위해서입니다.

## 흔한 실패

- 고정 길이 500자로 기계적으로 자르기 → 문장 중간이 잘려 임베딩 품질이 떨어짐
- 문서 전체를 한 청크로 → 검색은 되지만 관련 없는 내용까지 프롬프트에 들어가 비용과 노이즈 증가
- 프론트매터를 본문에 그대로 남겨 검색 → `tags: [개념]` 같은 문자열이 검색 점수를 오염시킴
