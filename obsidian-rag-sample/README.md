# 옵시디언 + RAG 위키 샘플

"LLM 위키 / RAG 위키"가 실제로 어떻게 굴러가는지 보여주는 **동작하는 최소 샘플**입니다.
샘플 볼트(마크다운 노트 12장)와, 그 위에서 도는 검색·생성 파이프라인이 들어 있습니다.

핵심은 한 문장입니다. **옵시디언 볼트는 그냥 마크다운 폴더이고, RAG는 그 폴더를 읽어 검색 색인을 만드는 것뿐입니다.**
특별한 포맷도, 서버도, 벡터DB도 처음부터 필요하지는 않습니다.

```
질문 ─▶ 검색(BM25 + 벡터 + 링크 그래프) ─▶ 상위 6개 청크 ─▶ 프롬프트 조립 ─▶ Claude ─▶ 답 + 출처
```

## 폴더 구조

```
obsidian-rag-sample/
├── vault/                       ← 옵시디언에서 "폴더를 볼트로 열기" 하면 바로 열립니다
│   ├── 00-INDEX/                   목차(MOC) 노트
│   ├── 10-개념/                    RAG·청킹·임베딩·하이브리드 검색·평가·캐싱
│   ├── 20-실무/                    볼트 작성 규약, 플러그인 선택, FAQ
│   ├── 30-기록/                    회의록·회고 (RAG가 특히 잘 먹히는 문서 유형)
│   └── 99-템플릿/
└── rag/
    ├── vault_index.py           마크다운 파싱 → 프론트매터·헤딩 청킹·위키링크 그래프
    ├── retriever.py             BM25 + 해싱 벡터 + RRF 융합 + 링크 확장
    ├── ask.py                   검색 → 프롬프트 조립 → Claude 호출 → 출처 표시
    ├── evaluate.py              Recall@k / MRR 로 검색 단계만 따로 측정
    ├── eval_questions.json      평가셋 17문항
    └── requirements.txt
```

## 바로 실행해 보기

검색과 평가는 **의존성이 하나도 없습니다**(표준 라이브러리만). API 키도 필요 없습니다.

```bash
cd rag

python3 vault_index.py                       # 색인 결과 확인 (노트/청크 수, 청크 길이 분포)
python3 retriever.py "청크는 얼마나 크게 잘라야 하나요"   # 검색만
python3 evaluate.py                          # Recall@6 / Top-1 / MRR
python3 ask.py "비공개 노트는 어떻게 막나요" --dry-run    # 조립된 프롬프트 확인 (API 호출 없음)
```

실제 답변 생성만 SDK와 키가 필요합니다.

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-...             # 또는 `ant auth login`
python3 ask.py "파일럿에서 약어 검색이 왜 실패했나"
python3 ask.py "..." --show-context          # 근거로 뭐가 들어갔는지 같이 보기
```

현재 이 샘플 볼트 기준 측정값입니다(`python3 evaluate.py`):

| 지표 | 값 |
| --- | --- |
| Recall@6 | 1.00 (17/17) |
| Top-1 정확도 | 0.82 |
| MRR | 0.912 |

k를 3으로 줄이면 Recall이 0.94로 떨어집니다. 이런 걸 감으로 정하지 않으려고 평가셋을 두는 겁니다.

## 파이프라인에서 실제로 중요한 결정 5가지

이 샘플을 만들면서 실제로 부딪힌 것들이고, 코드에 주석으로도 남겨 두었습니다.

1. **헤딩 기준 청킹** — 옵시디언 노트는 사람이 이미 헤딩으로 구조를 잡아둔 문서라 이 방식이 가장 잘 맞습니다.
   짧은 절은 합치고(200자 미만), 긴 절은 문단 경계에서 자르며(1200자 초과), 헤딩 줄은 본문에 남깁니다.
   헤딩을 지워버리면 FAQ의 "비공개 노트는 어떻게 막나요" 같은 소제목이 검색되지 않습니다.
2. **한국어 토큰화** — 형태소 분석기 없이, 한글은 문자 2-gram·영문은 단어 단위로 자릅니다.
   대신 `얼마나`, `하나요` 같은 기능어를 2-gram으로 자르기 **전에** 제거해야 합니다.
   안 그러면 `얼마`·`마나` 조각이 "희귀한 단어"로 취급돼 엉뚱한 문서가 1위로 올라옵니다. (실제로 겪었습니다.)
3. **RRF 융합은 상위 후보만** — 전체 순위를 융합하면 점수 간격이 뭉개져서, 뒤에 붙는 가산점 하나에 순위가 통째로 뒤집힙니다.
4. **링크 확장은 가산점이 아니라 '자리 배정'으로** — 상위 결과를 밀어내지 않고 마지막 2자리만 이웃 노트에 내줍니다.
   노리는 것은 정밀도가 아니라 재현율("개념 노트는 찾았는데 결론이 적힌 회의록을 놓치는" 문제)입니다.
   솔직히 말하면 **이 12장짜리 볼트에서는 지표 차이가 없습니다**(`--no-links` 로 확인 가능).
   노트가 수백 장 넘어가면 다시 재보고 유지 여부를 정하세요. 그게 평가셋이 있는 이유입니다.
5. **비공개 노트는 색인 단계에서 제외** — 프론트매터 `visibility: private`. 프롬프트로 "말하지 마"라고 막는 건 신뢰할 수 없습니다.

## 옵시디언 설치 및 볼트 열기

옵시디언은 GUI 데스크톱 앱이라 이 원격 컨테이너(화면 없는 리눅스)에는 설치해도 띄울 수가 없습니다.
그래서 **볼트를 폴더 그대로 만들어 두었습니다.** 로컬 PC에서 이렇게 열면 됩니다.

1. 설치 — [obsidian.md](https://obsidian.md/download)
   - macOS: `brew install --cask obsidian`
   - Windows: `winget install Obsidian.Obsidian`
   - Linux: 공식 사이트의 AppImage / `.deb` / `flatpak install flathub md.obsidian.Obsidian`
2. 이 저장소를 클론한 뒤, 옵시디언에서 **"폴더를 볼트로 열기"** → `obsidian-rag-sample/vault` 선택
3. 좌측 하단 그래프 뷰를 켜면 위키링크로 연결된 노트 그래프가 보입니다. 이 그래프를 검색 확장에 씁니다.

`.obsidian/` 설정 폴더는 옵시디언이 처음 열 때 자동으로 만듭니다. 저장소에 커밋할지는 취향입니다(팀 공용이면 커밋을 권장).

## 볼트에 LLM을 붙이는 세 가지 방식

| 방식 | 무엇 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 옵시디언 플러그인 | Smart Connections, Copilot for Obsidian 등 | 설치가 곧 완성 | 청킹·검색이 블랙박스라 튜닝·평가 불가 |
| B. 외부 파이프라인 | **이 저장소의 `rag/`** | 전부 통제 가능, 팀 서비스로 확장 | 코드를 관리해야 함 |
| C. 에이전트에게 폴더를 그대로 | Claude Code를 볼트에서 실행 | 색인 불필요, 노트 수정까지 가능 | 볼트가 크면 탐색 비용 |

개인용이면 A로 시작하고, 팀 위키가 되는 순간 B를 만들고, 노트 정리·리팩터링은 C에게 맡기는 조합이 무난합니다.
자세한 비교는 `vault/20-실무/옵시디언 플러그인 선택.md` 에 노트로도 있습니다(그 자체가 검색 대상이기도 합니다).

## 진짜 임베딩으로 갈아끼우기

기본값은 학습도 네트워크도 필요 없는 **해싱 임베딩**입니다(TF-IDF 가중 해싱 벡터).
오프라인에서 파이프라인 전체를 검증할 수 있지만, 단어가 다르고 뜻이 같은 문서는 못 잡습니다.

`retriever.py` 의 `embed()` 하나만 바꾸면 됩니다. 인터페이스는 `str -> list[float]`(L2 정규화) 그대로입니다.

- 상용 API: Voyage AI, Cohere 등
- 로컬 모델: `bge-m3`, `multilingual-e5` 계열 (한국어에 강하고 사내망에서 돌릴 수 있음)

Anthropic은 임베딩 엔드포인트를 제공하지 않습니다. **검색은 임베딩 제공자, 생성은 Claude** 로 나누는 구성이 일반적입니다.
어느 쪽을 고르든 `evaluate.py` 로 교체 전후 Recall을 비교해 보고 정하세요.

## 생성 단계에 대해

- 모델: `claude-opus-5` (`--model` 로 변경 가능)
- 적응형 사고(`thinking: {"type": "adaptive"}`) 사용
- 시스템 프롬프트에 `cache_control` 을 걸어 고정 접두부를 캐시합니다. 다만 접두부가 약 1,024토큰을 넘어야 실제로 캐시가 적용됩니다.
- 답변 규칙은 4개뿐입니다: **발췌 밖의 내용 금지 / 문장마다 `[n]` 인용 / 근거 없으면 모른다고 말하기 / 오래된 노트는 경고**.
  인용 없는 답은 실패로 취급하는 편이 운영이 편합니다.
- `--fallbacks` 는 안전 분류기 거절 시 서버측 모델 폴백을 쓰는 베타 옵션입니다. 이 환경에서 실제 호출로 검증하지 못해 기본값은 꺼져 있습니다.

## 다음에 붙일 것들

1. **질문 로그** — 무엇을 물었고 어떤 청크가 들어갔는지 남기기. 최고의 평가셋은 실제 질문 로그입니다.
2. **리랭킹** — 후보 30개 → 리랭커로 상위 5개. 정확도가 가장 크게 오르는 한 방입니다.
3. **최신성 가중치** — `updated` 기준. 지금은 프롬프트에 "(오래됨)" 표시만 합니다.
4. **권한 분리** — 사용자별로 색인 자체를 분리하거나 검색 단계에서 필터링.
5. **슬랙/웹 연동** — `ask.py` 의 함수를 그대로 감싸면 됩니다.
